\chapter{Evaluation and Testing}\label{chap:evaluation}

This chapter outlines the evaluation methodology used to assess CCRMS against the research questions in Chapter~\ref{chap:research-questions}. It focuses on \textbf{how} the system was evaluated; the results are presented in Chapter~\ref{chap:results}. This chapter covers the evaluation approach, the four-layer testing architecture, the eight test scenarios, the 11 KPIs, the testing infrastructure, and the validity considerations that inform our interpretation of the findings.

Table~\ref{tab:dsr-eval} classifies the same activities using the Framework for Evaluation in Design Science (FEDS) \citep{venableEtAl2016} and the evaluation methods of \citet{hevnerEtAl2004}. Every evaluation episode is artificial: it runs on a local testnet, in a simulator, or in a model, with no real creators or consumers. This places the evaluation in the FEDS Technical Risk and Efficacy strategy, which suits an artifact whose main design risks are technical and for which evaluation with real users and production systems would be prohibitively expensive. Formative episodes, chiefly the security audit and the tests that guided the design iterations, shaped the artifact; summative episodes report on it as built, with the code versions given in Section~\ref{sec:validity}. Because no evaluation was naturalistic, the results say nothing about adoption or user behavior.

We organize testing into four layers, each executed at the lowest applicable level of abstraction. Figure~\ref{fig:testing-layers} summarizes the stack; each layer is described below.

\node[layer, fill=orange!18, above=3pt of l2] (l3) {
    \textbf{Layer 3: Zombienet End-to-End}\\
    {\footnotesize Live Rococo-local relay chain; Para~A and Para~B connected via HRMP;
     7 automated \texttt{@polkadot/api} benchmark scripts producing JSON output.
     Primary evidence source for KPIs 1--8.

};
\end{tikzpicture}

The comparative benchmark is intentionally minimal, using Express.js for HTTP and SQL.js for in-process SQLite. A production centralized service adds network hops, replication and caching. Its per-request latency would be higher than this in-process baseline, while its aggregate throughput could be much higher through horizontal scaling. The baseline is therefore a best case for centralized latency and a conservative figure for centralized throughput; in both cases the gap to CCRMS is large enough that the conclusions do not depend on the exact values.

\section{Metrics and Key Performance Indicators}\label{sec:kpis}

Our evaluation uses 11 key performance indicators (KPIs) across four domains: technical, economic, security, and reliability. Each KPI includes a description, measurement methodology, originating source (the test scenario or activity that generates it), and a target value. These targets were set as stated design objectives during Phase~2 planning, informed by commercial comparators rather than by published academic benchmarks; they are treated throughout as reference points rather than strict pass/fail criteria. The inclusion latency target of two block intervals reflects the 6-second parachain block time of the test environment; the chain-growth target of 85\% is sized for a single-collator Zombienet topology.

\section{Validity and Limitations}\label{sec:validity}

\textbf{Internal validity.} We kept the test environment constant across runs, applied the same methodology to CCRMS and the centralized baseline, and ran the deterministic unit-test suite on every commit. The XCM latency benchmark was run ten times per operation and is reported as medians; the throughput, block-utilization, storage-growth and stress benchmarks were each run once, so their figures carry no measure of run-to-run variation.

Not every benchmark was re-run after every fix. The throughput, storage-growth and stress measurements (31 March--1 April 2026) predate the remediation of Findings~B and~E (2 April) and of Findings~I, J and~K (September 2026), and the XCM latency re-run (24 September) predates commit \texttt{a20ad8c}. The fixes add checks and change collection settings but do not change the per-item storage layout (Table~\ref{tab:storage-costs}); we expect their effect on the reported figures to be small but did not re-measure it. We redesigned and re-ran the reliability test on 28 September 2026 using the final pallet code (commit \texttt{d88ec4e}); it is the only measurement taken after all fixes.

\textbf{External validity.} This is the dimension in which our evaluation is most limited. Four constraints apply: (1) we measure in a local Zombienet environment with two relay-chain validators and no real network latency, so the figures serve as upper bounds within the test environment rather than predictive metrics for production; (2) the Snowbridge integration uses a local Ethereum stack rather than a public testnet, avoiding variability in block times, MEV, contention, and beacon chain reorganizations; (3) the figures come from a local testnet with one core per parachain; elastic scaling, which could increase throughput, was not tested; (4) our scale is modest, comprising up to 200 concurrent accounts and a few hundred content items, and empirical verification of linear storage growth at production scale has not yet been conducted.

\textbf{Construct validity.} The figure of 26.2 TPS is the inclusion rate our closed-loop client could sustain, a lower bound on capacity rather than a capacity measurement (Section~\ref{subsec:stress-test}), and it is insufficient to assess user-perceived performance, which also depends on wallet user experience, mempool latency, and RPC responsiveness. The 90\% net chain growth describes a single collator on one machine and says nothing about availability with several collators. The Monte Carlo simulation evaluates expected revenue using a probabilistic model; the input parameter sources and assumptions are documented in Appendix~\ref{app:monte-carlo}.

\textbf{Threats to validity.} (a)~\textbf{Selection bias:} the eight test scenarios may not capture production conditions such as high subscriber concurrency on a single content item, large multi-collator topologies, or extended multi-month uptime. (b)~\textbf{Measurement instrument bias:} any bug in \texttt{@polkadot/api} or \texttt{system.blockWeight} would propagate into our results; although the library is widely used, it is not bug-free. (c)~\textbf{Confirmation bias:} the author was responsible for designing, implementing, and evaluating the system; this risk is mitigated by using externally referenced KPI targets and by disclosing all scripts and raw results. (d)~\textbf{Single-author validation:} no external code review, third-party security audit, or benchmark validation has been conducted; we recognize this as a significant limitation and intend to address it in future work (Appendix~\ref{app:future-work}, E.1).

\section{Summary}\label{sec:chapter-6-summary}

The evaluation uses four testing layers, eight test scenarios, seven automated benchmarks, a Monte Carlo simulation, and 11 KPIs grounded in a measurement-focused philosophy. Section~\ref{sec:validity} outlines the primary validity constraints. Chapter~\ref{chap:results} presents the results.
