\chapter{Security and Coverage Findings}\label{app:security}

\section[Finding B: Authorization Gap]{Finding B: Authorization Gap in \texttt{xcm\_transfer\_ownership}}\label{sec:d-finding-b}

The original implementation performed only \texttt{ensure\_signed(origin)} and then looked up \texttt{Ownership[content\_id, from]}, burned the seller's NFT, and minted a new one for \texttt{to}. No check confirmed that the dispatch caller had any relationship to the \texttt{from} account, so any signed account could call the extrinsic with arbitrary \texttt{from} and \texttt{to} arguments and transfer ownership from any user to itself.

We rate this finding \textbf{High}. Exploitation requires only a signed account with sufficient balance for transaction fees, no relationship to the victim, and no prior state; the impact is unauthorized transfer of a permanent, transferable ownership right. We initially recorded the finding as Medium on the grounds that the affected extrinsic is reachable only through the cross-chain path in normal operation, but Finding~A establishes that the \texttt{xcm\_*} extrinsics are also callable locally by any signed account, which removes that mitigation.

Our remediation was \texttt{ensure!(authorizer == from,\allowbreak\ Error::<T>::Unauthorized)}, committed alongside unit test \texttt{security\_xcm\_transfer\_\allowbreak ownership\_\allowbreak rejects\_non\_owner}.

This remediation still permits genuine cross-chain transfers, but only by the owner's own chain-derived account. When a sibling parachain sends an XCM \texttt{Transact} from its own root, as in our benchmark, the call dispatches under that parachain's sovereign account, which can never equal \texttt{from}. When an ordinary user on the sibling chain signs \texttt{polkadotXcm.send}, \texttt{pallet-xcm} prepends \texttt{DescendOrigin(AccountId32)}, so CCRMS receives the origin \texttt{(1, [Parachain(n), AccountId32])}. The runtime's \texttt{LocationToAccountId} converts that location through \texttt{HashedDescription} into an account derived from the user's chain and key, and \texttt{Transact} with \texttt{SovereignAccount} kind dispatches under that derived account. If the derived account holds the ownership, the equality check holds remotely. Two xcm-simulator tests (commit \texttt{e258f1e}) confirm this: a signed Para~B user transfers ownership held by their derived account, and a second Para~B user attempting the same transfer is rejected with \texttt{Unauthorized} after the message executes under that user's own derived account. Three qualifications apply. First, the derived account is distinct from the same person's local CCRMS account, so ownership bought locally cannot be moved this way, and the derived account needs a CCRMS balance to pay execution fees. Second, CCRMS trusts the sending chain to prepend the correct \texttt{DescendOrigin}; a malicious or compromised sibling runtime could act as any of its own users, though not as users of another chain or of CCRMS itself. Third, the tests run in the xcm-simulator against a mock runtime aligned with the production XCM configuration; we did not repeat them on Zombienet. Appendix~\ref{sec:e-delegation} describes how XCM~v5 origin aliasing would let a remote user act as their local account.

\section{Finding E: View Pack Overwrite}\label{sec:d-finding-e}

The original \texttt{purchase\_views} always overwrote \texttt{ViewPacks[content\_id, buyer]} with a new \texttt{ViewPackInfo}, so a user holding 10 unused views who purchased 5 more would end up with 5, not 15. Our remediation made purchases additive: if a view pack already exists, new views are added to the existing balance.

This remediation initially covered the local \texttt{purchase\_views} path only; the XCM path (\texttt{xcm\_purchase\_views}) still overwrote \texttt{ViewPacks} and minted a fresh child NFT on each call, orphaning the previous one. Commit \texttt{a20ad8c} moved both paths onto a single shared purchase function, so cross-chain purchases are now additive as well. Regression tests: \texttt{security\_purchase\_views\_adds\_to\_existing\_pack}, \texttt{xcm\_purchase\_views\_adds\_to\_existing\_pack} and \texttt{local\_then\_xcm\_purchase\_views\_share\_one\_pack}.

\section{Accepted Design Findings (A, C, D)}\label{sec:d-accepted}

\textbf{Finding A:} \texttt{xcm\_*} extrinsics are callable locally as gift transactions (economically neutral; documented for transparency). \textbf{Finding C:} Runtime XCM \texttt{SafeCallFilter} is set to \texttt{Everything}; the \texttt{XcmExecuteFilter}, \texttt{XcmTeleportFilter}, and \texttt{XcmReserve\allowbreak TransferFilter} are similarly set to \texttt{Everything}, and \texttt{FixedWeightBounds} is used in place of measured XCM weights; production should restrict all four to explicit allowlists (this also inflates XCM fees; Appendix~\ref{sec:xcm-fee-scaling}). We rate this Low for the prototype because the reach of \texttt{Transact} is bounded by the origin converter, not by the filter: the runtime has no superuser conversion, so a remote \texttt{Transact} dispatches only as a signed sovereign or derived account, or as a relay-chain or sibling native origin, and, except from the relay chain, must pay for execution (\texttt{AllowTopLevelPaidExecutionFrom}). With a signed origin, a remote chain can do nothing a funded local account cannot. The remaining exposure is calls whose weight cannot be bounded before dispatch, which is what \texttt{SafeCallFilter} exists to exclude. If deployed unchanged, we would rate it Medium. \textbf{Finding D:} Content can be registered with all prices at zero (legitimate free-content feature, not a vulnerability).

\section{Finding I: Zero-View Denial of Service}\label{subsec:finding-i}

\textbf{Severity:} Medium. \textbf{Status:} Fixed (commit \texttt{a20ad8c}).

\textbf{Description.} \texttt{purchase\_views} accepted \texttt{num\_views = 0}, charged \texttt{ppv\_price} $\times$ 0 = 0, and still minted a child NFT. \texttt{consume\_view} then failed with \texttt{NoViewsRemaining}, so the slot was never released. Fifty throwaway accounts could permanently block all future sales of any content item for the cost of transaction fees alone.

\textbf{Remediation.} Both purchase paths now call a shared function that rejects \texttt{num\_views = 0} with a new \texttt{ZeroViews} error before any payment or minting. Regression tests: \texttt{security\_zero\_views\_purchase\_rejected} and \texttt{security\_xcm\_zero\_views\_purchase\_rejected}. The fix removed the free exploit; commit \texttt{2865ed0} later removed the bound itself (Appendix~\ref{sec:e-child-cap}).

\section[Finding J: Child-NFT Divergence]{Finding J: Child-NFT Divergence}\label{sec:d-finding-j}

\textbf{Severity:} High. \textbf{Status:} Fixed (commit \texttt{221e5fa}).

Collections were created with default \texttt{pallet-nfts} settings, which allow child NFTs to be transferred directly via \texttt{pallet-nfts} extrinsics. Because \texttt{pallet-content-rights} did not disable this capability, the holder could sell or transfer their child NFT through \texttt{pallet-nfts} while the \texttt{Ownership} storage map still named them; a later \texttt{transfer\_ownership} then burned the NFT from the buyer's wallet.

The fix creates all collections with \texttt{TransferableItems} disabled (only the runtime's ForceOrigin (root) can re-enable it) so child NFTs cannot be moved except through \texttt{transfer\_ownership}. Burn failures now propagate as errors rather than being silently ignored.

Regression tests: \texttt{child\_nft\_cannot\_be\_transferred\_via\_pallet\_nfts} and \texttt{transfer\_ownership\_works\_with\_non\_transferable\_children}.

\section[Finding K: Auto-Renewal Starvation]{Finding K: Auto-Renewal Starvation and Non-Atomic Payment}\label{sec:d-finding-k}

\textbf{Severity:} Medium. \textbf{Status:} Fixed (commit \texttt{221e5fa}).

The \texttt{on\_initialize} hook reads the first 20 entries of \texttt{AutoRenewIndex} (in storage-hash order) every block. It skips unexpired entries at the front, and expired entries beyond them are never reached (starvation). Separately, multi-recipient royalty payments were not wrapped in a storage transaction: if one payment failed, earlier payments in the same renewal were not rolled back, leaving the pallet in a partially-paid state. The fix introduces a \texttt{RenewalQueue} keyed by expiry block: each block processes only its own bucket (at most ten renewals), and overflow spills to the following blocks, searching up to 100 blocks ahead (about 1,000 renewals per expiry window).

Regression tests: the four existing auto-renewal group tests plus\\
\texttt{enable\_auto\_renew\_fails\_when\_queue\_full}.

\section[Finding L: Unbenchmarked Weights]{Finding L: Unbenchmarked Extrinsic Weights}\label{sec:d-finding-l}

\textbf{Severity:} Medium if deployed; Informational on the local testnet. \textbf{Status:} Open.

\textbf{Description.} Every weight in \texttt{pallet-content-rights} (13 functions in \texttt{weights.rs}) and in \texttt{pallet-rights-verifier} (three functions) is hand-set with \texttt{Weight::from\_parts(\ldots, 0)}: an estimated \texttt{ref\_time} plus database reads and writes, and a declared proof size of zero. The \texttt{on\_initialize} renewal hook also accounts only for database operations. The runtime's \texttt{StorageWeightReclaim} extension records the proof size each transaction actually consumed, which is why the proof-size figures in Section~\ref{subsec:block-weight} are measured, but it does so after dispatch. Fees and block admission use the declared weight, so on a live parachain the proof-size cost of a transaction is not charged and cannot be bounded before it executes, and the \texttt{ref\_time} figures are estimates rather than measurements.

\textbf{Remediation.} Benchmark both pallets with FRAME benchmarking, including worst cases (the maximum number of royalty splits, a full \texttt{RenewalQueue} bucket, the deepest Merkle proof), and replace the hand-set values with the generated weights. Benchmarking was outside the scope of the prototype; it is a prerequisite for deployment (Appendix~\ref{sec:e-production}).

\section[Finding M: Renewal-Queue Griefing]{Finding M: Renewal-Queue Griefing}\label{sec:d-finding-m}

\textbf{Severity:} Medium. \textbf{Status:} Fixed (commit \texttt{facc3dc}).

\textbf{Description.} The \texttt{RenewalQueue} introduced for Finding~K (Section~\ref{sec:d-finding-k}) is shared by all content: each block holds at most ten renewals, and \texttt{enqueue\_renewal} searches at most 100 blocks ahead. \texttt{enable\_auto\_renew} accepted content with any period. Keeping every bucket full needs about $10 \times \max(p, 100)$ queued entries for a period of $p$ blocks, so about 1,000 auto-renewing subscriptions with periods of 100 blocks or less would suffice; since the holder cap was removed (commit \texttt{2865ed0}) they can all target a single content item. The attacker pays the subscription price to themselves, and renewals in \texttt{on\_initialize} pay no transaction fee, so after the initial transactions the queue stays full at no further cost; a minimum price would not prevent this. While the queue is full, \texttt{enable\_auto\_renew} fails for every user with \texttt{RenewalQueueFull}, and existing subscribers lose auto-renewal when their next renewal cannot be queued. A period of zero also re-queued the entry into the bucket just processed, where it never ran again. We found this by code review; the attack was not executed.

\textbf{Remediation.} \texttt{enable\_auto\_renew} now rejects content whose period is below a new configuration constant, \texttt{MinAutoRenewPeriod} (14,400 blocks in the runtime, about one day at 6-second blocks), with a new \texttt{AutoRenewPeriodTooShort} error. Keeping the whole queue full then needs about 144,000 subscriptions. Content with a shorter period can still be registered, subscribed to and renewed manually. Regression tests: \texttt{enable\_auto\_renew\_rejects\_\allowbreak period\_below\_minimum} and \texttt{enable\_auto\_renew\_rejects\_\allowbreak zero\_period\_\allowbreak and\_accepts\_minimum}. A targeted variant remains: an attacker can still fill the 100-block window around one predictable expiry block, at a one-time cost of about 1,000 subscriptions per window. A refundable deposit per queued entry would raise that cost further.
